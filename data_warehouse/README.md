# dwh-dbt

The data warehouse. A dbt project that turns the `raw_*` tables produced by
[`dwh-config-local`](https://github.com/matheus-amon/dwh-config-local) into a star schema and
four B2B SaaS marts.

| Repo | Role |
|---|---|
| [`dwh-config-local`](https://github.com/matheus-amon/dwh-config-local) | Generates the synthetic accounts, subscriptions and product telemetry the raw layer is made of |
| **`dwh-dbt`** (this one) | Models that data: staging, core, marts, and the tests that keep them honest |
| [`dwh-airflow`](https://github.com/matheus-amon/dwh-airflow) | Runs the warehouse on a schedule and consumes its output as an Asset |

The project root is `data_warehouse/`; run dbt from there.

## The domain

B2B SaaS product analytics. The questions a SaaS data team actually gets asked:

- How is MRR moving — new, expansion, contraction, churn?
- Do cohorts retain, and does the revenue that leaks out come from the small accounts or the large ones?
- Which features get adopted, and by which tier?
- Which paying accounts are worth calling this week?

Domain entities: `account` (the B2B customer and billing unit), `user` (a person inside an account),
`plan`, `subscription` (a period on one plan), `product_event` (an action in the product).

## Running it

```bash
# 1. the raw layer — about a minute, a million events
cd ../dwh-config-local && make telemetry-up && make telemetry-generate && make telemetry-load

# 2. the warehouse
cd ../dwh-dbt/data_warehouse
pip install -r requirements.txt
cp <your dbt profile> ~/.dbt/profiles.yml     # profile name: saas_metrics_dw
dbt deps
dbt build
```

Postgres lives in `saas_dw` on port 5434. CI does the same thing on every push, generating the raw
layer from `dwh-config-local` rather than from a committed fixture — so if the two repositories
disagree about the schema, the build fails.

## Shape of the project

```
data_warehouse/
  dbt_project.yml            # one schema per layer; materialisation by folder
  packages.yml               # dbt_utils only — the date spine is this project's own macro
  macros/
    generate_date_spine.sql  # replaces dbt_date
    generate_schema_name.sql # keeps 'marts' meaning the marts schema
    safe_divide.sql
    months_between.sql
    generic_tests/
      expect_non_negative.sql
      expect_grain_unique.sql
  models/
    sources/_sources.yml      # 71 tests: the contract with dwh-config-local
    staging/                  # 5 views
    core/
      dimensions/             # dim_date, dim_accounts, dim_users, dim_plans
      facts/                  # fct_subscription_periods, fct_product_events (incremental),
                              # fct_account_weekly_usage
    marts/                    # 4 marts
  tests/                      # singular tests for the invariants that matter
```

22 models, 298 tests, 16 relations. Schemas: `staging` (views), `core` (tables), `marts`.

### Design decisions worth arguing about

**One schema per layer, verbatim.** dbt's default concatenates the custom schema with the target
schema, so `+schema: marts` against a profile called `public` yields `public_marts`. That makes the
schema depend on what the profile is called, which breaks the asset URIs the Airflow DAGs
reference. `generate_schema_name` is overridden to keep the name as written.

**No `dbt_date`.** The calendar is generated by a macro in this project. One fewer dependency, and
the attributes the marts read are declared here rather than inherited from a package's forty
columns.

**`safe_divide` returns NULL, not 0.** "No revenue over no customers" is unknown, not zero, and a
mart that reports it as 0 reads as "this segment produced nothing" when it actually never existed.
Where zero is the right answer the models coalesce explicitly, so the decision is visible.

**Terms, not a snapshot.** There is no SCD2 snapshot here. The subscription term table already *is*
the temporal structure — an upgrade closes one term and opens the next — and the raw layer is
rebuilt from scratch on every load, so a snapshot would see every attribute change each run and
produce a single meaningless version.

**`mrr_retention_index`, not `mrr_retention_rate`.** A cohort that expands after signing up holds
more revenue than it arrived with, so that measure legitimately exceeds 1. Naming it a rate invites
reading it as a bounded proportion. The boundedness test covers account retention, which is
genuinely bounded.

**Feature availability is a var, not an inference.** `feature_min_tier` in `dbt_project.yml` records
which tiers can reach which features. Without it, a gated feature reads as 0% adoption on the tiers
that cannot reach it, when the truth is that it is unreachable there. It is product catalogue data,
so it is declared rather than reverse-engineered from the telemetry — inferring it from events
would assume away the thing the adoption mart exists to check.

## The models

### Core

| Model | Grain | Notes |
|---|---|---|
| `fct_subscription_periods` | account × month | The central fact. MRR at month end plus new / expansion / contraction / churn flags. |
| `fct_product_events` | event | The only incremental model: `merge` on `event_id`, with a one-day lookback. |
| `fct_account_weekly_usage` | account × week | Weekly engagement, normalised per active user. |
| `dim_date` | day | Own spine macro, spanning past the data window so empty months still appear. |
| `dim_accounts`, `dim_users`, `dim_plans` | entity | Surrogate keys; `dim_users` carries `fk_account`. |

`fct_subscription_periods` collapses a mid-month plan change into a single row, because MRR is a
month-end snapshot. `terms_in_month` records that more than one term touched the month, so the
movement mart can still see the change happened.

`fct_product_events` filters on a one-day lookback rather than `> max(event_ts)`. A merge only
inserts and updates, never deletes, so a strict filter silently drops any event whose timestamp
trails the last one written. If the source is ever reseeded rather than appended to, re-run with
`--full-refresh` — orphans survive a merge, and this is documented on the model because it cost an
afternoon to find.

### Marts

| Mart | Grain | What it answers |
|---|---|---|
| `mart_mrr_movement` | month | How MRR is moving, with `beginning + net new = ending` reconciling exactly. |
| `mart_cohort_retention` | signup month × signup tier × month since signup | Whether the revenue that leaks out is small accounts or large ones. |
| `mart_product_adoption` | month × feature × plan tier | Adoption over the *entitled* set, not over the whole tier. |
| `mart_account_health` | paying account | Who is worth calling, scored on recency, frequency, trend and magnitude. |

**MRR movement reconciles to 0.00 across all 46 months.** Contraction and churn are positive
magnitudes that net new subtracts, which makes the identity assertable rather than approximate —
the cheapest proof that the buckets are complete and disjoint. Churned MRR is measured against each
account's *opening* balance, because an account that upgrades and churns in the same month has the
new plan's price at month end while what actually left was what was in the opening balance.

**Retention diverges from revenue on purpose.** In the current data, account retention at month 12
sits at 82–95% while the MRR index is above 100% for most tiers: the survivors expand enough to
offset the churn. Segregating by signup tier is what makes that visible — enterprise cohorts show
the opposite, losing revenue faster than accounts.

**The health scorecard is the mart the generator's behaviour model exists to feed.** Accounts that
churn have a decline in weekly usage in the weeks beforehand, so ranking on recency, frequency and
trend surfaces them before the revenue is gone. Scoring is deliberately transparent — four
components on 0–100, weights in `dbt_project.yml`. Frequency is weighted above magnitude because
declining engagement is the early signal and falling revenue is the late one.

## Tests

298 of them. The interesting ones are the singular tests in `tests/`, because they assert
properties that column-level tests cannot:

- `assert_mrr_movement_reconciles` — opening + net new = ending, exactly.
- `assert_movement_flags_are_mutually_exclusive` — the mart's buckets cannot double-count.
- `assert_cohort_periods_are_contiguous` — a cohort's periods run 1..n with no gaps, so a missing
  account cannot silently flatten the retention curve.
- `assert_marts_are_not_empty` — a mart that builds and contains nothing is the failure mode that
  compile checks and unit tests do not catch.
- `assert_feature_gating_holds_in_adoption` — no plan tier shows usage of a feature it cannot reach.
- `assert_every_event_has_a_subscription_period` — otherwise adoption is understated with no error.
- `assert_health_scores_are_bounded` — every component and the total on 0–100.
- `assert_churn_months_have_an_opening_balance` — churn cannot happen with nothing to remove.

Grain is asserted on the natural columns via `expect_grain_unique`, not on the surrogate key: the
key is derived from the grain, so a grain that silently changes would carry the hash with it and
keep passing.

## What the tests caught

Not a list of tests that pass — a list of bugs they found, since that is the part worth reading:

- `is_churn` is a property of a subscription *term*, so using it as a month-level event marked
  every month a churned term spanned as a churn month: 216 false positives.
- Churned MRR read from month-end MRR misstated churn by the size of a same-month plan change. The
  reconciliation test found it, at 768.75 unexplained.
- `rng.multinomial` normalises `pvals` along its last axis, so a 2-D probability array made the
  generator draw its whole event budget once per account.
- An `accepted_range` test with `inclusive: false` excludes the legitimate boundary values 1 and 4.
- The health score was scaled 100× because the weights already sum to one, which made every
  non-dormant account read as healthy.
- Adoption credited a whole month to the plan at month end, so an account that upgraded mid-month
  had gated-feature usage counted below the gate that entitles it.
